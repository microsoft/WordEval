WordEval:Evaluating Word-Native Operation Fidelity in Document Editing

WordEval evaluates agents on Word editing operations, with Word itself as the verifier. Each requested change is checked in the document's objects and properties, across 231 commands, alone and combined with other edits in one document.

Abstract

Microsoft Word is a central environment for office automation, and the faithful execution of its editing operations is an important capability for document agents. Unlike plain-text editing, editing in Word modifies a structured object model, where the requested effect is realized in object properties. Existing benchmarks, however, evaluate office workflows or desktop automation, treating Word documents as one domain among many and verifying outcomes with keywords, per-task property checks, or screenshots.

We introduce WordEval, an operation-fidelity benchmark that instead centers evaluation on Word editing operations, testing whether each requested edit is realized as intended changes to Word objects and properties. It contains 642 cases across 15 Word feature areas, ranging from text and lists to charts, shape geometry, and SmartArt. 546 atomic cases cover 231 commands, 96 compositional cases combine multiple edits in a single document, and a Word-native oracle checks task-specific object properties and preservation conditions. Cases are constructed from editing-unit specifications, yielding controlled input documents, reference documents, and aligned oracle checks. Each compositional case is linked to corresponding atomic cases, supporting fine-grained diagnosis of editing failures.

We evaluate eight agent systems and find that many struggle on the Atomic track, with performance varying across feature areas. Moreover, every system scores lower on Compositional than on Atomic, with gaps that vary substantially by system. Exact atomic-intent links and recorded failure diagnoses provide complementary views of this variation.

Benchmark

The task landscape

WordEval builds two kinds of task from the same editing units, covering 231 Word commands in 15 feature areas. An Atomic task asks for a single Word command on an input document built for it. A Compositional task combines several editing units in one document; the four composition classes group these tasks by how their units interact. Each unit of a Compositional task is an atomic intent, linked to the Atomic task that applies the same command, so a drop in score reflects combining edits rather than new commands. The benchmark contains 546 Atomic tasks and 96 Compositional tasks with 319 atomic intents.

Method

How WordEval checks an edit

WordEval judges the saved document, not the steps the agent took. Word opens the output, and an oracle reads the object properties the request should change, together with what should stay the same. A task passes only when every required check passes.

Coverage

What the oracle reads

Word represents a document as runtime objects with properties, such as Shape.Rotation or Font.Bold. For each Atomic task, the oracle reads the properties that its command should set. Across the 546 Atomic tasks, it reads 139 object properties on 65 runtime objects, shown here by feature area and runtime object.

Results

Key results

Eight agent systems run on the same 642 tasks. Claude Code with Opus 5 achieves the highest Overall Case pass rate at 87.1%, while the remaining systems score between 44.5% and 66.7%, and three human participants average 82.8%. All eight systems score lower on Compositional than on Atomic tasks.

Analysis

What the results reveal

We first compare Atomic performance across Word feature areas, then test whether success on individual edits carries over to combined requests, and finally break down how tasks fail.

RQ1: Where do agents succeed?

Performance depends strongly on the Word feature area. Tables and Paragraphs achieve the highest mean pass rates, at 83.2% and 81.1%, with strong performance on cell merging, row-height distribution, paragraph alignment, and indentation (Figure 6).

In contrast, Pictures has the lowest mean pass rate at 44.9%, followed by SmartArt (50.7%) and Page Structure (53.8%). These areas include image cropping, picture effects such as glow, bevel, and shadow, SmartArt node and formatting edits, and header and footer configuration. Image and diagram editing and page-level configuration thus remain harder than table and paragraph formatting.

RQ2: Can agents combine edits they can do alone?

Every system scores lower once edits are combined, but by different amounts. Compositional pass rates fall below Atomic ones by 3.2 to 19.1 points (Table 1). Systems that look alike on individual edits can diverge on combined requests. Gemini 3.8 Flash and GLM-5.2 pass 57.9% and 58.2% of Atomic tasks, but 49.0% and 39.6% of Compositional tasks.

By composition class. Scope-changing tasks have the highest pass rates for each system shown, from 58.3% to 100%. Layout-coupled tasks vary the most across systems, from 23.1% to 84.6% (Figure 7A).

Conditioned on atomic success. Restricting to cases whose linked Atomic tasks all pass raises additive pass rates by 41.6 points for K3 but only 2.3 points for GPT-5.6 (Figure 7B). Other classes are less uniform. On layout-coupled tasks, GPT-5.6 has a conditional pass rate of 66.7% against a raw rate of 76.9%, and GLM-5.2 passes only two of its eight eligible cases.

Passing each edit alone does not ensure passing them together.

RQ3: How do outcomes break down?

Systems fail in different ways. Some return documents that fail a requested check, while others fail before the requested edit can be evaluated at all (Figure 8A).

Incorrect output
For Opus 5, 59 of 83 non-passing cases are valid documents that fail a check, and none are invalid.
Invalid or missing
For GPT-5.6, invalid documents and missing outputs together account for 18.4% of all cases.
Missing output
Gemini 3.8 Flash ends 41.7% of all cases, 268 of 642, without a submitted document, including runs stopped at the 600-second limit.

Most incorrect outputs contain the requested element but differ in its settings or Word structure. Among the 59 incorrect outputs of Opus 5, 23 are property-value mismatches and 20 are structure mismatches (Figure 8B). A shadow preset or a footnote numbering format may differ, and in the sin x and ln x equations Opus 5 inserts an invisible function-application character (U+2061) that leaves the rendering unchanged, so a screenshot cannot show it.
